# 01 产品愿景

## 1. 产品定义

Soul Mobile Agent Workbench 是一个以自然语言为主要控制方式的 Android Mobile Agent Runtime 与工作台。

用户描述要达到的结果，系统负责持续观察设备、形成阶段目标、执行设备动作、验证真实结果，并把可理解的进度和最终结果反馈给用户。

它不是一组按 App 编写的固定自动化脚本，也不是一个要求用户管理模型、Prompt、Token 和 ADB 命令的工程控制台。

## 2. 核心体验

产品第一原则：

> 聊天是操作界面，其余一切都是可展开的执行详情。

用户可以直接说：

```text
打开设置，看看现在的电池信息，告诉我以后回到桌面。
```

执行中也可以继续说：

```text
先停一下。
```

```text
我自己操作，等会儿再继续。
```

```text
不用继续找了，直接回桌面。
```

这些不是孤立的新聊天，而是对当前 Active Task 的实时控制输入。

## 3. 用户可见的产品层

正常使用时，界面只需要呈现：

- 用户与 Soul 的消息；
- 当前设备连接状态；
- 当前任务与当前阶段的简短状态；
- 必要的暂停、继续、取消和接管入口；
- 一个“查看执行详情”的展开入口。

展开后才展示：手机实时画面、最近动作、Runtime 状态、所用模型角色、事件流和 ADB 日志。调试信息帮助解释“发生了什么”，但不是完成任务所必需的主流程。

## 4. 用户价值

### 4.1 从步骤控制转向目标控制

用户不需要知道某个按钮坐标、页面层级或 ADB 命令，只需要表达目标和约束。

### 4.2 过程可打断、可理解

系统不是一次性黑箱调用。用户能看到当前阶段，并通过自然语言或明确控件调整、暂停、取消或接管。

### 4.3 结果以真实设备状态为准

系统不会因为发送了一个点击命令就宣称成功。动作之后必须重新观察并验证目标状态。

### 4.4 多入口共享同一能力

Web 工作台、Hermes、微信未来都只是 Client。无论从哪里发起或继续任务，背后都进入同一个 Runtime Gateway 和 Task Runtime。

## 5. 产品设计原则

1. **自然语言优先**：用户表达目标、限制和修正，不编排技术步骤。
2. **事实优先**：Runtime 中的任务状态来自 Observation、执行结果和验证，不来自模型自我声明。
3. **渐进呈现**：默认展示对用户有用的信息，工程细节按需展开。
4. **角色与模型解耦**：产品只依赖 Planner、Operator、Language 能力，不依赖某个模型品牌。
5. **通用闭环优先**：MVP 验证通用观察与操作能力，不为首个任务写固定流程。
6. **用户持续拥有控制权**：任务运行不取消暂停、取消、接管和修改约束的能力。
7. **简单优先**：在真实需求证明必要之前，不增加复杂任务图、多 Agent 编排或庞大权限系统。

## 6. 首个 MVP 场景

首个正式任务固定为：

```text
自然语言指令
→ 打开 Android 设置
→ 进入电池页面
→ 读取当前可见的电池信息
→ 将结果反馈给用户
→ 返回桌面
```

这个场景同时证明：自然语言目标进入 Runtime、阶段规划、基于当前画面的操作、观察融合、结果读取、独立验证、语言反馈和任务收尾。

关键约束是：不得使用为“设置 → 电池”预先编写的坐标序列、页面路径脚本或设备专用点击流程。

## 7. 成功的产品形态

MVP 成功不是“前端看起来像聊天”，也不是“模型偶尔点对一次”。成功意味着用户从统一入口发出目标后，Runtime 产生可追踪任务，在真实 Android 设备上完成通用闭环，验证结果，反馈可核对的信息，并在用户要求下回到桌面。

更远期能力不是本基线的承诺。它们只有在 MVP 真实运行后、由新的产品决定明确进入范围，才能成为后续设计输入。
