# 16 Codex 执行协议

## 1. 三方决策权

### 用户

用户决定：

- 要什么；
- 不要什么；
- 产品边界；
- 预期效果；
- 什么算完成；
- 最终取舍与是否进入下一阶段。

### ChatGPT / 设计者

设计者决定：

- 如何理解当前项目；
- 为达到效果采用什么技术路线；
- 如何拆分可验证成果；
- 修改哪些模块与不修改哪些模块；
- 接口、架构和验证方法；
- 给 Codex 的当前施工单。

### Codex

Codex 负责：

- 阅读完成施工单所需的代码和文档；
- 在授权范围内实现；
- 运行测试和实际验证；
- 报告真实修改、证据、偏差与问题；
- 在完成一个可验证成果后 STOP；
- 遇到新架构决策时提前 STOP。

## 2. 核心规则

> Codex 获得的是一张有限范围的施工许可证，不是整个项目的自主设计权。

Codex 可以发现问题、解释影响和提出候选方案，但不能因为发现问题就自行改变设计。

Codex 可以决定局部实现细节，但不能改变技术路线、公共契约、模块职责、产品边界或验收含义。

## 3. 正常停止点

正常停止点是一个可验证成果完成，而不是每改一个文件，也不是整个项目一次做完。

```text
施工单
  ↓
实现
  ↓
验证
  ↓
成果报告
  ↓
STOP
```

完成后，Codex 可以列出可能的下一步作为信息，但不能自动生成并执行下一张施工单。

## 4. 提前停止条件

出现以下任一情况立即停止当前实施：

- 需要改变已确认的产品边界或效果；
- 需要新增核心抽象、服务、状态或角色；
- 需要改变公共 API、数据持久化语义或模块所有权；
- 当前设计与真实代码结构发生职责冲突；
- 必须修改施工单的 Out of Scope；
- 出现两个以上会产生长期影响的架构方案；
- 验收标准无法按既定方案实现；
- 需要不可逆或超出授权范围的操作；
- 发现现有工作区改动与任务重叠，无法安全绕开。

## 5. 施工单模板

```text
TASK
本阶段要交付的一个可验证成果

WHY
该成果在整体方案中的作用

CURRENT STATE
已确认的工程事实

GOAL
本阶段结束时系统具备的能力

IN SCOPE
- 允许修改或实现的内容

OUT OF SCOPE
- 明确不做的内容

DESIGN
- 已决定的技术边界、接口与依赖方向

IMPLEMENTATION FREEDOM
- Codex 可自行决定的局部实现细节

MUST STOP IF
- 本施工单特有的提前停止条件

VERIFY
- 自动测试
- 集成或真机验证
- 需要保存的证据

DONE WHEN
- 可核对的完成条件

AFTER DONE
STOP。不要自行进入下一阶段。
```

## 6. 执行前

Codex 应：

1. 阅读仓库级指令和当前施工单指定文档；
2. 记录分支、HEAD、工作区状态；
3. 识别并保留用户已有改动；
4. 确认本阶段 In Scope / Out of Scope；
5. 做必要的只读现状检查；
6. 如果实际情况要求新架构决定，直接报告 Blocker，不开始越界修改。

## 7. 执行中

Codex 可以在施工单范围内连续完成 3～5 个明确步骤，不需要每个文件都请求审批。它应保持修改最小、保留现有行为、用事实验证假设，并在发现偏差时更新执行说明。

Codex 不得：

- 顺手重构无关模块；
- 为未来需求提前铺设复杂系统；
- 把具体模型写死到核心契约；
- 用测试通过替代真机验收；
- 用运行状态替代产品效果确认；
- 清理、重置、提交或推送用户工作区，除非施工单明确授权。

## 8. 架构阻塞报告模板

```text
ARCHITECTURE_BLOCKER

发现
已确认的代码或运行事实

影响
为什么继续会改变当前设计或范围

候选
A. ...
B. ...

已完成
停止前已安全完成的内容

未执行
为避免越权而没有执行的内容

当前施工单状态
PAUSED / NOT STARTED
```

候选方案只提供判断材料，Codex 不替用户和设计者选择。

## 9. 完成报告模板

```text
RESULT
本施工单交付的可验证成果

CHANGES
- 修改文件与行为

VERIFICATION
- 自动测试及结果
- 真实运行/设备证据及结果

BOUNDARY
- 明确未做的内容

DEVIATIONS
- 与施工单的偏差；没有则写无

OPEN FINDINGS
- 新发现但未擅自处理的问题

STATUS
DONE — STOP
```

## 10. 证据层必须分开

完成报告分别说明：

1. Artifact：代码或文档是否已产生；
2. Tests：哪些测试通过；
3. Runtime：真实服务或设备运行到了什么状态；
4. Acceptance：用户定义的效果是否获得真实验收；
5. Publication/Deployment：如适用，是否真正部署或发布。

任何一层不能自动证明另一层。

## 11. 本文档包之后的第一张施工单

本文只提供设计基线，不自动授权工程实现。建议第一张施工单是“现状与工程基线”或“Runtime Skeleton + ADB Observation/Action + Event Store”中的一个经过进一步限定的可验证成果。具体选择由用户与设计者在看到真实仓库后决定。
