# 20 待决定问题与非目标

## 1. 使用方式

本文防止实现阶段把尚未决定的问题偷偷变成架构。待决定项不阻止与其无关的施工单；当某项成为当前成果的必要前提时，Codex 必须按执行协议提前 STOP，由用户与设计者决定。

## 2. MVP 前必须结合真实仓库决定

### Q1. 现有代码从哪里切入？

- 当前是否已有可复用的 ADB、设备管理、聊天或任务代码？
- 是在现有服务内建立 Runtime 模块，还是存在明确的新服务边界？

这需要先做只读仓库现状地图，本文不猜测。

### Q2. v0.1 的持久化实现是什么？

逻辑上需要 Task Snapshot、Event 和 Checkpoint；具体使用现有数据库、轻量数据库还是其他仓库已有设施，待现状检查后决定。

### Q3. 角色 Adapter 的首选实现是什么？

Planner、Operator、Language 的接口已经确定，但具体本地/云端模型、推理服务、结构化输出能力和降级顺序需要根据可用环境实测选择。不得把示例模型写死为架构。

### Q4. Verify 机制由规则还是角色辅助实现？

Verify 的独立语义已经确定；具体实现可以使用可观测规则、现有模型角色提供的辅助判断或两者组合，但不增加第四个核心模型角色。必须保证 Verify 基于动作后的新 Observation，且不能把动作执行结果或 Operator 的自我声明直接视为成功。

### Q5. Gateway 的认证与部署网络是什么？

统一入口和 Client 关联已确定，但本地部署、远程访问、认证方式和 TLS 边界取决于实际部署环境。

### Q6. Hermes / 微信的实际接入条件是什么？

需要确认现有 Hermes 能力、微信通道、消息限制和部署方式。契约模拟通过与真实微信通过必须分开报告。

### Q7. 数据保留配置是什么？

事件、截图、UI Tree、模型原始响应和 ADB 日志的默认保留期限、空间上限与清理方式待部署决定。

### Q8. 无进度、超时和升级阈值是多少？

机制已确定，具体数字应由真机测试校准，不能仅凭文档拍定。

### Q9. 首个支持设备与 Android 版本是什么？

MVP 需要指定一台基线设备作为真实验收环境。单机通过不自动声明所有厂商与版本兼容。

### Q10. Workbench 的前端技术栈是什么？

界面原则和 Gateway 契约已确定，具体框架应优先服从现有仓库事实。

## 3. MVP 之后才讨论的问题

- 多设备并发与设备调度；
- 同设备任务队列和优先级；
- 长期用户记忆；
- 完整 Skill 生命周期与分发；
- Android 之外的桌面或浏览器环境；
- 自动生成训练数据与模型训练；
- 复杂高风险动作分类与确认策略；
- 多租户和企业权限；
- 大规模远程部署与运营；
- 游戏场景的长时间操作和专用能力。

这些不是隐含路线图，也不应为它们提前增加抽象。

## 4. 明确非目标

v0.1 不做：

1. **固定 App 脚本平台**：不以每个 App 的点击流程为产品核心。
2. **通用流程编排器**：不引入 DAG、BPMN 或复杂工作流 UI。
3. **Agent Swarm**：Planner、Operator、Language 是角色，不是互相自治的 Agent 团队。
4. **全自动软件开发治理系统**：Codex 协议是工程执行边界，不是要在产品 Runtime 内实现一套 Codex 管理平台。
5. **模型管理中心**：Router 只解决运行时角色绑定，不建设模型市场。
6. **Prompt IDE**：不把 Prompt 调试做成主产品界面。
7. **长期人格系统**：Task Facts 和 Checkpoint 不自动成为人格记忆。
8. **完整 Android 兼容承诺**：MVP 只对明确验收设备和环境提供证据。
9. **微信专用 Runtime**：Hermes/微信只是 Client，不复制核心能力。
10. **以日志代替事实**：ADB 日志、模型文本和前端状态不替代 Runtime Event 与 Verify 证据。

## 5. 不得由实现方擅自回答的问题

以下问题一旦出现，属于新产品或架构决定：

- 是否增加新的核心 Role；
- 是否让 Client 直接操作设备；
- 是否引入 App 专用 Action / Skill；
- 是否把模型推断写入长期记忆；
- 是否增加新的强制用户确认或安全限制；
- 是否改变 `SUCCESS / FAIL / UNCERTAIN`；
- 是否允许未 Verify 就 Commit；
- 是否让 Codex 自动开始下一阶段；
- 是否把 Android 之外的环境纳入 MVP。

## 6. 决策记录格式

当待决定项被正式决定时，建议记录：

```text
Decision
决定了什么

Owner Intent
用户要求的边界与效果

Technical Choice
设计者选择的技术方案

Consequences
对当前文档、接口和路线图的影响

Effective From
从哪张施工单开始生效
```

决策完成后更新受影响文档，而不是只留在聊天或实现代码中。
