# 通用 Android 长任务验收标准

## 目的

本文定义 AI-GAME 长期 Android 能力的 black-box acceptance（黑盒验收），描述用户看见的结果，不规定某个 App 的专用实现。

首个代表场景使用用户的一句话：

> 帮我在 Soul 上匹配，然后找到合适我的女朋友。

这里的 Soul 是第三方 Android App，只是首个真实环境。它不是已经退出产品方向的 AI-GAME 内部 Soul 页面、专用工作台或 dating copilot（约会副驾驶）。通过验收的实现必须仍是通用 Android 长任务能力；以后更换为游戏、购物、内容或其他社交 App 时，不应重写一套顶层系统。

这个场景不能保证另一个真人作出特定选择，也不能把匹配、一次回复或一次约会冒充“找到女朋友”。顶层目标保持运行，直到用户确认结果、修改目标、暂停、接管或停止。只有用户可以确认现实关系结果已经达成。

## 一句话到任务单

用户只需要先说结果，不需要先选择模型、runner（执行器）、Profile（模拟器配置）、端口或运行模式。

DeepSeek Harness（DSH，执行智能体运行时）在原 WeftMate 对话中完成以下工作：

1. 理解目标，并检查当前可靠记忆中已经存在且仍适用的信息；
2. 进行 adaptive clarification（自适应澄清），询问达到可执行状态所需的最少充分问题；
3. 把答案整理为用户可读、可修改、可确认的 task brief（任务单）；
4. 在用户确认任务单和真实动作授权范围后，提交一个权威长期 Task；
5. 后续只在缺少事实、出现需要用户选择的分支或触及授权边界时回到原对话提问。

“问 10 个问题”是交互尺度示例，不是固定数量、上限或表单。系统可以一次问一组，也可以根据答案继续追问；已有的可靠答案不应机械重问。首轮澄清至少覆盖与当前目标相关的内容：

- 什么叫“合适”，什么才算最终完成；
- 双方均为法定成年人的资格条件、地区/距离和关系目标；
- 重要偏好、价值观、生活方式与明确排除项；
- 允许系统查看、筛选、喜欢、草拟消息或直接发送到什么范围；
- 可使用的真实个人资料、表达语气和不得代替用户编造的内容；
- 哪些决定必须再次询问，例如见面、金钱、隐私、亲密关系或其他高影响承诺；
- 运行时间、通知方式、等待节奏、暂停/接管方式和停止条件。

任务单至少包含：原始目标、当前完成条件、已确认事实、偏好与排除项、动作授权范围、停止/升级条件、可修订的任务步骤、当前状态和 revision（修订）身份。DSH 拥有用户可见任务单与通用规划；AI-GAME 只维护 Android 执行所需的局部步骤、等待、恢复点和证据，不建立第二套聊天或审批界面。

## 自主思考、聊天与手机操作

这不是 task list executor（任务清单执行器）或自动点击器。用户确认任务单和授权范围以后，系统必须作为 autonomous agent（自主智能体）继续工作，而不是把每一次资料判断、消息回复和页面选择都退回给用户。

在每次唤醒中，它应当自己完成闭环：

```text
观察当前手机画面与当前会话
-> 结合任务单、候选人资料、聊天上下文和已验证经验进行推理
-> 判断现在应该筛选、喜欢、开始聊天、继续回复、等待、换策略还是向用户补问
-> 自己组织符合用户真实信息与授权语气的消息
-> 通过通用 Android UI 操作完成输入和发送
-> 重新观察，确认消息、页面和会话状态确实发生了预期变化
-> 保存当前会话状态并决定下一次等待或动作
```

“像一个真人一样操作手机”在验收中具体表示：使用普通用户可见的 App 界面和输入路径；理解含糊页面与非预期跳转；记住不同候选人的独立上下文；面对真实、未预录的回复生成有上下文的后续消息；控制节奏并在适当时等待；从误点、页面更新、App 被关闭和进程重启中恢复。它不依赖隐藏的 Soul 专用 API、固定坐标、预写聊天树或开发者现场代点。

系统可以在用户一次性授权的范围内自主筛选、发起和继续多段对话，不需要逐条消息再审批。只有缺少真实个人事实、出现多个会显著改变结果的选择、将要越过授权范围或涉及用户明确要求保留给自己的决定时，才使用结构化问题回到原 WeftMate 对话。

自主聊天必须同时满足以下可验证事实：

- 每条候选人会话有独立、持久且不会串线的上下文；
- 回复基于当前最新消息、任务目标和用户提供的真实事实，不照搬固定模板；
- 模型可以主动决定暂不回复、结束无效会话、调整话题或等待，而不是看到输入就机械发送；
- 任务被暂停、修改、接管或停止后，迟到的模型结果不能继续发送；
- 无法确认事实时明确询问或使用不作虚假陈述的表达，不能编造用户经历、身份、承诺或感情；
- 一次发送的通道回执不算完成，必须重新观察正确账号、正确对象和实际消息状态。

“像真人一样”不等于伪造真人经历、绕过平台规则或刻意规避自动化识别。真实 dogfood 使用什么披露方式和自动化范围，应在当时适用的 App 规则与用户授权中冻结；系统本身不能用欺骗来补齐未知事实。

## 长期执行合同

确认后的典型执行顺序由答案动态生成，而不是写死为 Soul 脚本。它通常会包括：

1. 检查受管后端、模拟器、App、账号和个人资料是否就绪；
2. 按冻结条件发现和筛选候选人；
3. 在授权范围内执行喜欢、跳过、草拟或发送消息等动作；
4. 等待外部回复，并通过时间或事件重新唤醒；
5. 根据新页面、回复和用户反馈更新局部计划；
6. 在需要用户判断时返回原 WeftMate 对话，而不是擅自越过边界；
7. 持续运行到真实完成条件、用户控制或明确不可继续状态。

一次 DSH turn（对话轮次）结束、工具 HTTP 等待结束或用户切换页面，都不能取消 Task。关闭窗口时应按产品可见策略继续后台运行或持久保存并在受管启动后恢复；显式退出或 Windows 重启后的行为必须如实显示，不能假装一直运行。不得要求用户手工开关 `127.0.0.1:4310`。

运行时可以有很多次有界 wake（唤醒）：每次先确认 owner、Task revision、Profile、设备身份和 fresh observation（新鲜观察），再规划一个可验证动作，动作后重新观察。顶层目标没有固定动作数或迭代数；可控性来自暂停、停止、接管、等待、退避、无进展检测、幂等和真实终止条件。

页面变化、一次误判、App 退出、网络波动、无人回复或模型一次失败属于运行时恢复问题，不应自动变成项目层面的“继续找 Bug、继续改代码”。工程阶段形成固定 candidate（候选）并完成有限内部验证后，必须交给产品所有者 dogfood（亲自试用）并停下等待反馈。

## 学习与复用合同

“自己学习”只有在后续行为真的改变时才成立，不能用保存日志、增长数据库或模型口头声称代替。

AI-GAME 保存 execution experience（执行经验）：经过后置观察验证的页面状态、动作结果、失败原因、恢复办法和完成证据。经验必须与 owner、目标判据、Profile、设备、App 包/版本和环境兼容范围绑定；未经验证、结果不确定或环境已不兼容的经验不能升级为捷径。

MemoWeft 保存 personal memory（个人记忆）：用户明确表达并允许保留的稳定偏好、排除项、沟通风格和事后反馈。AI-GAME 不复制个人世界；在 MemoWeft 接缝尚未交付前，只能把这些事实留在当前 DSH 任务上下文中，并如实说明不能跨任务长期复用。

回复、无回复、用户喜欢或拒绝分别是不同证据。“对方没回复”不能被系统单独推断成某一项人格偏好，也不能未经用户反馈给真人打隐蔽分数。

第二次相似任务必须提供 retrieval proof（检索证明）：

- 显示检索到的兼容经验身份和适用范围；
- 证明至少一个澄清、计划、动作选择或恢复路径实际使用了该经验；
- 与第一次基线相比，至少在重复提问数、首个有效动作耗时、失败动作数或恢复次数中的一项有可复核改善；
- 环境不兼容时拒绝复用，而不是为了指标强套旧经验；
- 改善不能以增加重复消息、错误账号动作或其他真实副作用为代价。

学习 Soul 的实际导航和交互规律可以成为有范围经验；把 Soul 坐标、候选人、固定问卷或成功答案写进产品代码，不算学习。

## 真人交互与执行完整性

浏览、喜欢、发送消息和约见会影响真人。首轮问题必须让用户明确授权范围，系统随后可以在该范围内连续执行，不应每一步重复审批；超出范围时回到原对话询问。

无论授权多宽，系统都不能：

- 使用错误账号、错误设备、错误候选人或过期任务修订执行动作；
- 重复发送、批量骚扰、虚构用户身份/经历或对对方作出故意虚假的事实陈述；
- 未经明确确认替用户作出见面、金钱、隐私、亲密关系或其他高影响承诺；
- 抓取或外传与任务无关的个人资料；
- 在没有设备证据和用户确认时声称匹配、关系或任务成功。

真实 dogfood 前必须检查当时适用的 App 规则、账号状态和用户授权；本文不把任何会变化的第三方规则固化成永远正确的产品事实。

## PASS 分层

以下证据不能互相替代：

| 层级 | 必须证明的事实 |
| --- | --- |
| 对话与任务单 | 从一句自然语言目标开始，完成自适应澄清，用户确认任务单、权限和结束条件；不暴露内部配置术语 |
| 工程合同 | 权威 Task、revision、等待/唤醒、暂停/继续/修改/接管/停止、观察/动作/验证和经验接口通过对应测试 |
| 产品候选 | WeftMate 自主管理 AI-GAME 生命周期和模拟器 Profile；用户无需操作 4310；状态、问题、控制和结果都回到原对话 |
| 真实模拟器 | 在指定 Android 模拟器和真实 App 上，以新鲜观察、动作回执和后置验证完成获授权动作；面对至少一段未预录的真实会话能自主生成有上下文的后续消息，并能等待后恢复 |
| 首轮长期任务 | 在固定候选上持续推进到用户设定的中间里程碑、真实完成、或诚实的等待/需用户输入状态；无四类完整性阻断 |
| 第二轮学习 | 检索兼容经验、实际影响计划或动作，并至少有一项可量化改善；不兼容经验被拒绝 |
| 现实结果 | 只有用户确认某段现实关系满足目标，才能报告“找到合适的女朋友” |
| 产品所有者 PASS | 产品所有者对这个固定候选和环境明确给出 `PASS`；测试绿灯、HTTP 可达或开发者代操作都不能替代 |

四类 `BLOCKING_NOW`（当前阻断）仍然只有：不可控的重复真实副作用、owner/Task/Profile/设备身份串线、凭据或敏感数据暴露、无证据却伪造成功。其他问题记录为 `KNOWN ISSUE`（已知问题）或 `DEFER`（延后），由产品所有者的实际 `FAIL` 决定当前候选是否需要修复。

## 防止为验收作弊

首个场景不得通过以下方式达标：

- 恢复旧 AI-GAME Soul 页面、旧专用 owner、dating-copilot 或第二套聊天/任务中心；
- 增加 Soul 专用 runner、硬编码坐标、固定候选人、固定十问、预写聊天树或固定成功路径；
- 使用 fake backend（模拟后端）、预录画面、测试数据库或人工代点冒充真实模拟器证据；
- 把一次工具调用、一次匹配、一次回复、经验记录写入或模型自述当作顶层完成；
- 为了通过测试增加任意“最多 2 步”、固定 action budget（动作预算）或隐藏的开发者开关；
- 在交付候选后自动扩大范围并进入无限工程修复循环。

这个标准是首个高价值场景，不是唯一能力清单。后续场景可以更换 App 和目标，但必须继续验证同一条主链：一句话目标 → 充分澄清 → 可控任务单 → 持久执行 → 证据闭环 → 经验复用 → 用户确认结果。
